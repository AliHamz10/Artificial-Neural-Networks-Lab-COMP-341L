Abstract

This lab develops and evaluates a domain-specific academic assistant for explaining Computer Science concepts in a consistent course-specific teaching style. A small causal language model (distilgpt2) is fine-tuned using LoRA adapters on a manually curated instruction-response dataset. We compare base vs fine-tuned outputs using a fixed evaluation prompt (“Explain dynamic programming”), analyze failure cases (hallucination, repetition, off-topic content), and perform one manual improvement iteration by refining the dataset.

Note: All dataset explanations were written manually. Model outputs are presented as raw evidence, followed by human analysis and reasoning.

Keywords

LLM fine-tuning, LoRA, PEFT, distilgpt2, instruction tuning, hallucination, teaching style.

1. Introduction

General-purpose chatbots often respond with generic explanations, inconsistent tone, and may hallucinate details when a prompt is underspecified. In an academic setting, a course assistant must be both clear and style-consistent, and ideally reduce overconfident guessing. This lab targets style control via small-scale instruction tuning.

2. Teaching Style Definition (Part 2)

Strict teaching style template (enforced in the dataset):
  • Step-by-step explanation (numbered)
  • Analogy (real-life)
  • Tiny example (1–3 lines)
  • Common mistake / misconception
  • Recap (one-line summary)

The goal is to teach the model a repeatable structure that improves readability for beginners and makes answers predictable for grading and classroom use.

4. Model Selection (Part 3)

Selected model: distilgpt2 (small causal LM). It is suitable for a classroom lab because it trains quickly on limited compute and makes fine-tuning behavior observable.

Advantages: small, fast iteration, coherent short-form responses.

Limitations: weak factual reliability, limited reasoning depth, prone to repetition and off-topic text when data is small or decoding is stochastic.

5. Fine-Tuning Strategy (Part 4)

Method: LoRA (Low-Rank Adaptation) via PEFT. Instead of updating all model parameters, LoRA learns low-rank adapter matrices for selected attention projections. This reduces GPU memory usage and makes training feasible in Colab.

Why LoRA here:
  • Trains fewer parameters → faster and cheaper
  • Less risk of catastrophic forgetting in the base model
  • Adapters can be saved/loaded independently for comparison

6. Experimental Setup

  • Prompt format: ### Instruction: ... ### Response:
  • Fine-tuning objective: next-token prediction (causal LM) on formatted instruction-response text
  • Evaluation prompt (fixed): “Explain dynamic programming in a step-by-step, analogy-based teaching style.”
  • Decoding: sampling enabled (temperature=0.7, top_p=0.9)

7.4 Critical comparison (analysis)

Clarity: Base output is short but does not explain dynamic programming. Fine-tuned v1/v2 outputs are verbose but largely off-topic and repetitive, failing to follow the intended teaching structure.

Hallucination reduction: The tuned models did not become more cautious; instead they produced “article-like” filler text. This indicates the fine-tuning did not successfully imprint the desired format.

Style consistency: The strict template (steps + analogy + example + mistake + recap) is not consistently produced. This suggests either (i) the dataset is too small for stable behavioral change, (ii) training overfit to noise patterns, or (iii) decoding settings increased repetition.

8. Failure Analysis (Part 6)

Two failure prompts were used to diagnose behavior. Raw outputs are stored in JSON files and summarized here.

Failure case 1: “Prove DP always gives optimal answer”

Observed failure: Both tuned models avoid an actual proof and instead generate irrelevant, repetitive filler.

Why it failed: The dataset teaches explanation style but does not include proof-like answers, formal assumptions (optimal substructure), or examples of when a “proof request” should be answered carefully.

Cause category: primarily data limitation (missing proof-oriented examples) plus model limitation (small model).

Failure case 2: “Exact best-known TSP complexity + year”

Observed failure: The base model replies with a vague update statement; tuned models generate confident-sounding content (including a suspicious arXiv link) without actually answering precisely.

Why it failed: The prompt requests precise external facts (algorithm details + discovery year). A small model may guess, and the fine-tuning set lacks examples that teach “I’m not sure / I don’t have a citation.”

Cause category: model limitation + training data does not include uncertainty handling.

9. Manual Improvement (Part 7)

A manual improvement iteration was performed by creating dataset_cs_instructions_v2.jsonl, focusing on:

  • Explicit “how to choose a DP state” examples (reduces vague DP answers)
  • Examples explaining why small LLMs hallucinate and how to respond cautiously

Result: In the captured v2 evaluation output, repetition increased rather than decreasing. This suggests that the fix was insufficient because the improvement set is extremely small (5 items) and cannot counteract instability from stochastic decoding.

Recommendations (what to try next)

  • Increase dataset size (e.g., 80–200 high-quality style-consistent samples) with more DP-focused items.
  • Use deterministic evaluation (greedy decoding) for fair comparisons; keep sampling only for creativity tests.
  • Add “refusal / uncertainty” examples to discourage confident guessing when asked for citations/years.
  • Lower learning rate / epochs to reduce repetition; add early stopping on training loss trends.
  • Use a slightly stronger small model (e.g., GPT-2 medium) if compute allows.

10. Conclusion

This lab demonstrates that fine-tuning a small LLM with very limited data can fail to reliably enforce a desired teaching style. The most important practical insight is that dataset quality and quantity dominate: to achieve consistent behavior, we need more diverse, high-signal examples aligned with the target tasks and evaluation prompts.
